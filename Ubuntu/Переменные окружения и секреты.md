# Переменные окружения и секреты

Одна и та же идея — «конфиг и секреты не в коде» — работает по-разному в каждом инструменте базы.

## Кто и откуда читает переменные

| Инструмент | Откуда берёт | Заметка |
| --- | --- | --- |
| shell | `export VAR=...`, `~/.bashrc` | — |
| direnv | `.envrc` при заходе в папку (`direnv allow`) | [[install direnv]] |
| Taskfile | `dotenv: ['.env']`, `env:` | [[Taskfiles]] |
| Docker compose | `env_file:`, `environment:`, подстановка `${VAR}` из `.env` | [[Docker compose шаблон Postgres и приложение]] |
| Python | `os.environ["VAR"]` / pydantic-settings | [[base_uv]] |
| Go | `os.Getenv("VAR")` | [[Go start]] |
| Alembic | URL БД из окружения в `env.py` | [[Alembic start]] |

## Приоритет (общее правило)

Переменная, уже заданная в окружении процесса, **не перезаписывается** значением из `.env`. Для Taskfile это описано в [[Taskfiles]]: кто первый загрузился, тот и победил.

## Что делать с секретами

1. `.env` в `.gitignore`, в репозитории — `.env.example` без значений.
2. Не вшивать секреты в код (пример антипаттерна: ключ JWT в коде, см. [[jwt]]).
3. Не использовать пароли по умолчанию на проде и не публиковать порт БД ([[Порты, и действия с ними]]).
4. SSH-ключи — права `600` ([[ssh]], [[chmod]]).
5. Если секрет попал в git — считать скомпрометированным: **перевыпустить**, а не просто удалить коммит.

## Паттерн: `.env.example`

```bash
# .env.example — копируется в .env и заполняется
POSTGRES_USER=
POSTGRES_PASSWORD=
POSTGRES_DB=
DATABASE_URL=
JWT_SECRET=
```

```bash
cp .env.example .env
```
